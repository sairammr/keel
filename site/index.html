01 — the leak

Your liquidation bot has a number — the health factor at which it acts. Put it in a TEE and call it private? Every action / inaction pair leaks one bit of a binary search. Three actions locate a fixed threshold to ±0.005 HF. With the public on-chain reserve, that is a stop-hunt target.

The whole game is played in a $205 window — HF 1.114 ⇔ $2,000 down to HF 1.00 ⇔ $1,795.

02 — the jitter

So the trigger refuses to be a number. trigger = clamp(base + k·σ + jitter(HMAC(salt, round))) One fresh draw per price level. Upward only — Keel can act earlier, never later. Cleverness never costs survival. No sequence of observations narrows base below the jitter width. The adversary knows the algorithm — Kerckhoffs — and still can't aim.

ii · receipts

Every action carries a receipt

EIP-712, signed by a key derived inside the enclave from the same salt. Action at nonce n, receipt at n+1, same EOA — visible on Etherscan. The receipt carries no trigger fields.

iii · reveal

Reveal, and anyone re-derives everything

Paste (policyBytes, salt). The commitment must match. Then every round's trigger is recomputed from public PriceUpdate logs and each action checked against the committed policy.

the verdict

ALL ROUNDS CONSISTENT

The independent verifier does not trust the receipts' self-reported HF — it reconstructs pre-action HF from chain logs. A mismatch would surface as RECEIPT HF MISMATCH. It didn't.

That is the difference between secrecy and verifiable secrecy.

06 — run it yourself

Anyone can check the keel.

Verify the live run

git clone https://github.com/sairammr/keel
bun install
bun run verify     # → ALL ROUNDS CONSISTENT
(cd app && bun run dev)   # /verify /hunter /replay

Simulate the enclave

cre workflow simulate workflow \
  --target staging-settings \
  --non-interactive --trigger-index 0

Runs the confidential handlerInTee under the CRE runtime — no deploy access needed.
